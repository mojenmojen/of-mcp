# Plan — #136: cap TypeScript at 5.8.x, then refresh the live server

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans (Native execution, decision 8). Steps use checkbox (`- [ ]`) syntax for tracking.

Date: 2026-10-30
Branch: `worktree-fix-136-pin-typescript`
Base: `e9dd11e` (v2.1.0)
Status: approved 2026-10-30. **What shipped is `~5.6.3`, not the `~5.8.3` this plan describes.** The Task 1 gate showed that TypeScript 5.8.3 also runs out of memory against MCP SDK 1.25.2, so the fallback applies: read 5.6 for 5.8 throughout (see Global constraints). Do not restore `~5.8.3`.

**Goal:** A plain `npm ci` gives a working toolchain (`npm run build`, `npm run build:fast` and `npm test`), and the live server runs current `main` on the dependencies the lockfile names.

**Architecture:** Cap the `typescript` devDependency so the lockfile resolves to 5.8.x instead of 5.9.3, and add a test that fails if the cap is lifted. After the merge, reinstall the main checkout's `node_modules` from the lockfile and rebuild the live server.

**Tech stack:** npm 11.9.0, Node v24.14.0, TypeScript, esbuild 0.27.2, `node:test`.

**Spec:** issue #136, suggested fix 1, narrowed to `~5.8.3` by the issue's comment of 2026-09-23. There is no separate spec.

## Why

The main checkout's `node_modules` was installed on 2025-07-31 and has never been reinstalled. esbuild became a devDependency on 2026-01-19 (#87), so it was never installed there, and `build:fast` and `npm test` only run with a borrowed binary on `PATH`. Nobody reinstalled because the lockfile pins TypeScript 5.9.3, which runs out of memory type-checking this project (#136). The old install happens to hold a working 5.8.3.

A dry run on 2026-10-30 showed that npm can't add esbuild on its own. `npm install --no-save esbuild@0.27.2` would bring the whole tree in line with the lockfile (27 added, 21 changed, 5 removed), including TypeScript 5.8.3 → 5.9.3.

The same stale install is why the live server runs MCP SDK 1.17.0. The bundle leaves the SDK and zod out (`--external`), so the server loads them from `node_modules` at start-up. The lockfile, and every test run in a fresh worktree, uses SDK 1.25.2.

**The evidence for 5.8.3 has a gap that Task 1 closes first.** The 2026-09-23 comment on #136 says the 5.8.3 and 5.9.3 runs differed only in the compiler version. That is wrong. The 5.8.3 runs used the main checkout's `node_modules`, with SDK 1.17.0's type definitions. The 5.9.3 runs used a worktree installed from the lockfile, with SDK 1.25.2. TypeScript 5.8.3 has never been run against SDK 1.25.2. The original report did verify 5.6.3 against the lockfile's dependencies, which is why it is the fallback.

On 2026-10-30, `tsc --noEmit` with 5.8.3 against SDK 1.17.0 type-checked current `main` (`e9dd11e`) in 0.67 s, exit 0.

## Decisions

Approving the plan confirms these. Any of them can be vetoed.

1. **Cap at `~5.8.3`, with `~5.6.3` as the fallback.** 5.8.3 is the newest version known to work on this code, and it is what the main checkout already runs. If it fails against SDK 1.25.2 (Task 1, Step 2), 5.6.3 is the only other version verified against the lockfile's dependencies. `~` allows 5.8.x patch releases only; 5.8.3 is currently the last one.
2. **A test pins the cap.** The lockfile drifted to 5.9.3 unnoticed once, during #134. `tests/toolchain.test.mjs` reads `package.json` and `package-lock.json`, so it needs no build and runs under `npm test`. Its failure message says how to raise the cap safely.
3. **The lockfile is regenerated by npm on top of `npm ci`, never by deleting it.** Deleting it would let every other dependency float. Installing over an exact copy of the lockfile changes only the requested package, and Step 6 checks that.
4. **Version 2.1.1 (patch).** No tool behaves differently. The change fixes the build.
5. **The live server is rebuilt with `build:fast`, not the full `tsc` build.** It produces the same single-bundle output as every earlier live build. The only thing that changes at restart is then the SDK version.
6. **The old `node_modules` is moved, not deleted, to `~/dev/of-mcp-notes/node_modules-2025-07-31`.** That folder is on the same volume, so the move is instant. It is outside the repo, so it doesn't mark the build as dirty. Restoring it takes one command. Deleting the backup later is MoJen's call.
7. **The docs change only where the cap makes them wrong.** `docs/TSC_OOM_TROUBLESHOOTING.md` gets a "Known cause" section and three corrected instructions, not a rewrite.
8. **Native execution.** I implement the tasks in this session and pause after each one for MoJen. One fresh reviewer then checks the whole branch before the PR. The tasks are small and sequential, and the real risks are environmental, which explicit gate steps cover.
9. **The PR description corrects the 2026-09-23 comment.** There is no separate comment on #136, because the PR closes the issue and its description is the lasting record.
