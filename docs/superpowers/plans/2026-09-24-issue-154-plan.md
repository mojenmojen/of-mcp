## Decision on bundling #152

**Both issues go in one change.** #154's second rung is "a timed-out write must say it
may have landed". #152 is the reason no message from `executeOmniFocusScript` reaches
the caller at all: the thrown value is a plain object, so every handler that unwraps a
caught value prints `[object Object]` or nothing. Counted on this tree: 54 sites use
`error instanceof Error ? error.message : String(error)` and 13 use
`: 'Unknown error'` — **67 unwrap sites across 45 files**, since several files use both
idioms and adding the two sets of files would double-count them. (61 files in `src/`
do some form of `instanceof Error ?` unwrap.) Fixing #154's wording without #152 would
produce a better message that nobody ever sees.

The bundle is small because the thrown value has exactly one origin
(`src/utils/scriptExecution.ts:241`) and exactly one consumer that reads its fields
(`src/tools/primitives/batchAddItems.ts:183`). Wrapping at the throw site fixes all 67
unwrap sites with no edits to them.

## What is wrong, confirmed from source

- `EXEC_OPTIONS.timeout` kills the `osascript` subprocess at 30s
  (`src/utils/scriptExecution.ts:19`). Killing the subprocess does not cancel the
  OmniJS script already running inside OmniFocus.
- `createTimeoutError` sets `retryable: true` (`src/utils/errors.ts:82`).
- `shouldRetry` retries anything retryable up to `MAX_RETRIES = 3`
  (`src/utils/scriptExecution.ts:30-33`, `:223`), with no idea whether the script
  writes.

1 attempt + 3 retries = the four folders observed. The arithmetic also matches the
timing in the issue: 30 + 1 + 30 + 2 + 30 + 4 + 30 ≈ 127s, which is why the call ran
past the client's 120s limit.

`executeJXA` shares `EXEC_OPTIONS` but has no retry loop, and its only callers are the
four read paths in `src/utils/perspectiveEngine.ts`. It needs no change.

## Scope

In: rungs 1 and 2 of the issue's ladder, plus #152.

Out, and staying on the issues:

- **Rung 3 (after a timeout, re-query and report success if the object is there).**
  Under the exact conditions that trigger it OmniFocus is pegged, so the confirming
  read times out too — the issue's own log shows the follow-up `get_folder_by_id`
  also exceeded 120s. It would also need per-tool identity logic (name + parent for
  folders, name + folder for projects, name + project + parent for tasks). It is a
  separate change, worth doing once rungs 1 and 2 stop the bleeding.
- **Rung 4 (idempotency keys or `failIfExists`).** Larger, and duplicate names are
  legal in OmniFocus, so the default has to stay permissive.

## The change

### 1. Classify every OmniJS script — new `src/utils/retryPolicy.ts`

A pure module (no node imports, so it bundles cleanly for tests) holding:

- `RETRY_SAFE_SCRIPTS`: the script filenames that are safe to repeat after a timeout.
- `isRetrySafeScript(scriptPath)`: accepts `'@name.js'`, a bare name or an absolute
  path, and compares on basename.
- `shouldRetry(error, attempt, scriptPath)`, moved here from `scriptExecution.ts`.

**Anything not listed is treated as unsafe.** A new script added later loses timeout
retries until someone classifies it, which is the harmless direction to fail.

The 31 script files and the 31 `'@name.js'` strings in the TypeScript are in exact
1:1 correspondence today, so the list can be pinned by a test.

Not safe to repeat (11): `addFolder`, `addProject`, `addTask`, `batchAddItems`,
`batchEditItems`, `batchMarkReviewed`, `batchRemoveItems`, `duplicateProject`,
`editItem`, `editTag`, `removeTask`.

Also not safe (1, a judgement call): `getCustomPerspectiveTasks`. It reads no less
safely than the others, but `ignoreFocus` (on by default) sets `document.focus = null`
and restores it in a `finally`. A run OmniFocus never finishes leaves Focus cleared; a
retry then reads that `null` as the original, so `focusWasActive` is false and it
neither re-clears nor restores. It reports `focus: {wasActive: false, cleared: false}`
for a window that did have a Focus — the Focus is lost and the caller is told it never
existed. The cost of excluding it is that one read tool loses timeout retries.

**Corrected after review:** an earlier draft of this paragraph said the retry would
"restore the wrong thing". Traced through the script, it restores nothing: the guard is
`if (focusCleared && originalFocus)` and both are falsy on the retry. The harm is the
silent loss plus the false report, not a wrong restore.

Safe to repeat (19): `batchFilterTasks`, `completionStats`, `diagnoseConnection`,
`filterTasks`, `flaggedTasks`, `forecastTasks`, `getChecksum`, `getFolderByName`,
`getProjectByName`, `getProjectsForReview`, `getTaskByIdOrName`, `inboxTasks`,
`listCustomPerspectives`, `listProjects`, `listTags`, `searchTasks`, `systemHealth`,
`tasksByTag`, `todayCompletedTasks`.

I grepped all 20 read-classified scripts for `new Task(`/`new Project(`/`new Folder(`/
`new Tag(`, `deleteObject`, `markComplete`, `markIncomplete`, `moveSections`,
`moveTasks`, `markReviewed`, `drop(` and `duplicate`. The only hit was a comment in
`listProjects.js`.

### 2. Gate the retry on timeouts only

```ts
if (attempt >= MAX_RETRIES) return false;
if (!error.error.retryable) return false;
if (error.error.type === 'timeout' && !isRetrySafeScript(scriptPath)) return false;
return true;
```

`app_unavailable` stays retryable for writes: if OmniFocus is not running, the script
never ran, so repeating it cannot duplicate anything. Only a timeout is ambiguous.

### 3. Say that the write may have landed

A new factory in `errors.ts` for the write case. It keeps `type: 'timeout'`, so any
type-based matching still works, and takes a new code `TIMEOUT_WRITE_UNVERIFIED`.

Message: `Script execution timed out after 30 seconds. The change may still have been
applied.`

Instructions:

1. `OmniFocus may be unresponsive or busy syncing.`
2. `This was NOT retried: a timeout does not mean the change failed.`
3. `Check OmniFocus before running this again — running it again may create a duplicate.`

Reads keep today's wording.

### 4. #152 — throw an `Error`

```ts
export class OmniFocusError extends Error implements StructuredError {
  readonly success = false as const;
  readonly error: StructuredError['error'];
  constructor(structured: StructuredError) {
    super(structured.error.message);
    this.name = 'OmniFocusError';
    this.error = structured.error;
  }
}
```

`success` and `error` are own enumerable properties, so `isStructuredError` keeps
recognising it and `JSON.stringify` keeps working. `scriptExecution.ts:241` throws
`new OmniFocusError(structuredError)` instead of the bare object. The factory
functions keep returning plain data, because `createValidationError` is also used as
a return value rather than thrown (`batchAddItems.ts:136` is the one throw, and it is
caught locally).

Every handler that does `error instanceof Error ? error.message : ...` starts printing
the real message with no edit to any of the 45 files.

### 5. #152 — `diagnose_connection` matches on type

`src/tools/primitives/diagnoseConnection.ts:66-95` currently sniffs the lowercased
message for `timed out`, `not authorized`, `not running` and so on. Against
`[object object]` none of them can ever match, which is why every script failure fell
into the `Unknown error` branch. Switch the branches to `isStructuredError(error)` and
`error.error.type`, keep the string matching as the fallback for non-structured
errors, and surface `error.error.instructions` when present.

## Review findings addressed

An agent review of the PR raised three Important findings, all accepted and
fixed on the branch:

1. **The diagnostic retried itself when OmniFocus was wedged.** `diagnoseConnection.js`
   was listed as safe to repeat, so the full ladder ran about 127 seconds — past
   the two minutes a client waits, and in the very scenario the tool exists for.
   It is now a read that is not repeated.
2. **"Not safe to repeat" was doing duty for "is a write".** One predicate
   answered two different questions, so a timeout on `get_custom_perspective_tasks`,
   a read, would have warned about creating a duplicate it could never create.
   `isRetrySafeScript()` and `mayHaveWritten()` are now separate, derived from
   `READ_SCRIPTS` and `WRITE_SCRIPTS` with the not-repeatable reads listed as
   explicit exceptions alongside their reasons.
3. **The wiring had no test.** The two behaviours met in three lines of
   `scriptExecution.ts` that nothing exercised. The rewrite is now the pure
   `finalizeTimeoutError()`, unit-tested directly.

Two cheaper suggestions were taken as well: the safe list is now checked by
content, so a script containing a mutation call cannot sit in it unnoticed, and
`tests/scriptExecution.test.mjs` notes that the test bundles each carry their own
copy of the error class.

Left for later, with the reviewer's agreement: the "30 seconds" string appearing
in three places rather than being derived, an unreachable AppleEvent `-1712`
timeout, `name` now appearing in the serialised error, and a README line.
